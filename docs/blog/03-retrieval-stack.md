# 03 · 检索栈：稀疏 / 稠密 / 混合，向量库与重排怎么配

## 当时业务痛点

知识库上线两周，客服反馈两极：有的问题「秒准」，有的「答得像相关其实完全不是」。典型翻车：

- 用户甩 **订单号 / 政策编号**，向量检索漂到语义相近的旧政策。
- 用户问「退款多久到账」，同义表达很多，纯关键词又漏召回。
- top-5 里混进权限不该看的文档，答案一本正经泄密风险。
- 换了「更大 embedding 模型」账单涨了，差评率几乎不动。

痛点本质：**召回目标混杂（精确 ID vs 语义意图）**，却只用一路检索；**排序目标与生成目标脱节**（相关 ≠ 可引用、可授权）。

## 当时怎么看这个问题

向量库营销话术容易让人以为「embedding 搞定搜索」。信息检索几十年经验是：稀疏与稠密互补，重排吃的是候选质量，生成吃的是重排后的可引用片段。工程上要分开优化 **Recall@k（候选）** 与 **Faithfulness / 引用正确率（生成）**。

## 试过什么

1. **只用稠密 + FAISS/Chroma**：语义题尚可；ID / 型号 / 错误拼写惨。
2. **只用 BM25 / 倒排**：专有名词强；同义改写弱。
3. **线性加权稀疏分 + 稠密分**：量纲不同，调参玄学。
4. **RRF（倒数排名融合）再交叉编码器重排**：更稳；重排模型贵、要控候选宽度。
5. **托管向量库一把梭**：运维省心；索引策略、混合检索、权限过滤仍要自己设计。
6. **pgvector 塞进业务 Postgres**：事务与备份统一；超大规模 ANN 与隔离要评估。

## 为什么否决

| 选项 | 原因 |
|------|------|
| **稠密替代稀疏** | 否决。精确匹配场景不可丢。 |
| **分数直接相加当融合** | 否决默认做法。不同路分量纲与分布差一个数量级。 |
| **重排吃全库** | 否决。交叉编码器只能吃小候选集（如 50～200）。 |
| **「换更大向量模型」当银弹** | 否决。先修切块、元数据过滤、混合与评测集。 |
| **无权限过滤的统一索引** | 否决上生产。检索层必须能按租户/角色裁剪。 |

## 最终怎么解

推荐默认管道（可按规模裁剪）：

```
查询理解（改写/纠错，可选）
  → 并行：稀疏召回 ‖ 稠密召回（各路带元数据过滤）
  → 融合（优先 RRF）→ 去重
  → 重排（交叉编码器或业务规则）
  → 上下文组装（引用、长度预算）→ 生成
```

### 向量存储对比（摘要）

| 选项 | 优点 | 缺点 | 什么场景选 |
|------|------|------|------------|
| **FAISS（本地）** | 快、可控、实验友好 | 自管持久化/复制 | 单机实验、批建索引 |
| **Chroma 等嵌入式** | 上手快 | 生产韧性与治理要自补 | Proto / 小团队 |
| **pgvector** | 与业务库一体、SQL 过滤强 | 极大规模 ANN、运维权衡 | 中小规模、强过滤 |
| **托管向量库** | 省运维、常带混合检索 | 成本、锁商、合规出境 | 要快速生产、团队小 |

### 检索范式

| 范式 | 优点 | 缺点 | 场景 |
|------|------|------|------|
| 稀疏 BM25 | 精确、可解释 | 同义弱 | ID、型号、法规条款号 |
| 稠密 embedding | 语义、多语言 | 精确弱、要语料匹配 | 自然语言意图 |
| 混合 + RRF | 互补稳 | 管道复杂 | **默认生产** |
| 重排 | 提精准 | 贵、增延迟 | 候选≥20 且质量敏感 |

## 用到的具体 skill / 技巧清单

| Skill | 用法 |
|-------|------|
| **先元数据过滤再 ANN** | 租户/时间/类型裁剪，缩小污染 |
| **RRF 优于裸分数相加** | 用排名融合避开量纲 |
| **切块服务引用** | 块太大难定位，太碎丢上下文 |
| **黄金集分意图** | ID 类 / 语义类 / 混合类分开算召回 |
| **重排宽度与延迟预算** | k_retrieve 与 rerank 模型级联选型 |
| **权限在检索层执行** | 不靠模型「不要泄露」 |
